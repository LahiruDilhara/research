\section{Chapter Overview}
\label{sec:req_chapter_overview}
Building a reliable, fast, and customizable paper-based virtual keyboard requires a clear System Requirement Specification (SRS). Developing vision-based human-computer interaction software without physical switches requires careful systems analysis. This ensures that camera tracking, hand joint normalization, homography calculation, and deep learning touch detection satisfy practical user needs \cite{ReviewVirtualKeyboard2020, Maman2023TypeNet}.

This chapter presents the requirements and UML models for the two-application system: Application 1 (Layout Designer Suite \texttt{designer/designer\_app.py}) and Application 2 (Runtime Virtual Keyboard Engine and Command Mapper). Section~\ref{sec:req_stakeholder} provides a stakeholder analysis, identifying user groups along with a Power-Interest matrix and design trade-offs. Section~\ref{sec:req_operationalization} explains the operationalization process, showing how research objectives and test data map to software requirements. Section~\ref{sec:req_uml_analysis} presents a full UML analysis, including Use Case diagrams with formal specifications, Class diagrams with Class Responsibility Collaboration (CRC) descriptions, Activity diagrams, Sequence diagrams, Statechart diagrams, and Deployment diagrams. Section~\ref{sec:req_architecture} explains the overall system architecture framework and design patterns. Section~\ref{sec:req_fn_nfn} details the Functional and Non-Functional requirements. Finally, Section~\ref{sec:req_summary} summarizes the chapter.

\section{Stakeholder Analysis}
\label{sec:req_stakeholder}
Stakeholder analysis identifies the people, groups, and systems that use or are affected by the virtual keyboard. Understanding stakeholder expectations ensures the system addresses real user needs \cite{ReviewVirtualKeyboard2020}.

\subsection{Stakeholder Identification and Classification}
\label{subsec:req_stakeholder_classification}
Stakeholders for the paper virtual keyboard system are divided into four main groups:
\begin{enumerate}
    \item \textbf{Primary End-Users:} People who directly type on the printed paper sheets to enter text or control computers. This group includes everyday computer users, regular typists, and users with motor difficulties who need custom large-key layouts \cite{Chen2024Gaze}.
    \item \textbf{Domain-Specific Specialists:} Professional users in specialized fields (such as digital audio editors, video editors, industrial machine operators, and CAD designers) who need custom macro pads for specific software shortcuts \cite{ReviewVirtualKeyboard2020}.
    \item \textbf{Healthcare and Clinical Staff:} Doctors, nurses, and laboratory technicians working in sterile environments where regular plastic keyboards can collect dirt and spread bacteria \cite{ReviewVirtualKeyboard2020}.
    \item \textbf{System Engineers and Researchers:} Computer vision researchers, software developers, and system administrators who design layouts, configure XML files, train neural touch models (\texttt{run\_all.py}), and maintain the runtime software.
\end{enumerate}

\subsection{Stakeholder Conflict Resolution and Requirement Trade-offs}
\label{subsec:req_conflict_resolution}
Differences in stakeholder priorities were resolved through practical engineering trade-offs:
\begin{enumerate}
    \item \textbf{Typing Speed vs Computing Load (Typists vs Administrators):} Typists need low delay, while administrators want the software to run on standard computers without high CPU load. This was resolved by using a 12~FPS video standard (\texttt{resample\_12fps.py}) and a compact PyTorch LSTM model ($< 1$~MB), ensuring real-time response on standard CPUs without requiring a GPU.
    \item \textbf{Custom Layouts vs Tracking Stability (Domain Specialists vs Vision Researchers):} Custom macro layouts can have keys placed near corners, which might cover tracking markers. This was solved by placing AprilTag markers along the outer margins, requiring only four visible corners to calculate homography matrix $H$.
    \item \textbf{Paper Disposal vs Profile Persistence (Medical Staff vs System Admins):} Resolved by storing layout geometries in XML files, allowing paper sheets to be thrown away or reprinted at any time without having to reconfigure the computer.
\end{enumerate}

Class Responsibility Collaboration (CRC) breakdowns for core system classes are explained below:
\begin{enumerate}
    \item \textbf{\texttt{LayoutDesignerApp}:} Responsible for managing the PySide6 canvas, tracking graphical button objects, and invoking export functions. Collaborates with \texttt{KeyButtonGraphic} and export utilities.
    \item \textbf{\texttt{RuntimeKeyboardEngine}:} Acts as the main coordinator for background vision processing. Manages threads, calls hand pose tracking, and dispatches key events. Collaborates with \texttt{CameraThread}, \texttt{MediaPipePoseExtractor}, and \texttt{KeyActionDispatcher}.
    \item \textbf{\texttt{ScaleNormalizationEngine}:} Shifts joint coordinates relative to the wrist $\mathbf{P}_0$ and computes unitless scale ratios using hand length $L_{\text{hand}}$. Collaborates with \texttt{SlidingWindowBuffer}.
    \item \textbf{\texttt{HomographyMappingEngine}:} Takes sub-pixel AprilTag corner points and calculates matrix $H \in \mathbb{R}^{3 \times 3}$ using SVD. Collaborates with \texttt{AprilTagTracker} and \texttt{KeyActionDispatcher}.
\end{enumerate}

\label{sec:req_architecture}
The proposed system architecture is organized as a two-application software suite.

Figure~\ref{fig:system_architecture_framework} presents the System Architecture Framework Diagram showing data flow between Application 1 (Layout Designer Suite) and Application 2 (Runtime Virtual Keyboard Engine and Command Mapper).

\begin{figure}[htbp]
\centering

\includegraphics[width=0.85\textwidth]{figures/chapter04_fig09.png}

\caption{Proposed System Architecture Framework Diagram highlighting Application 1 and Application 2 synchronized workflows.}
\label{fig:system_architecture_framework}
\end{figure}

As shown in Figure~\ref{fig:system_architecture_framework}, the design separation keeps layout authoring distinct from live camera processing:
\begin{itemize}
    \item \textbf{Application 1 (Layout Designer Suite):} Desktop GUI tool that exports printable vector PDF layouts with border AprilTag markers on normal paper, together with XML layout coordinate definitions.
    \item \textbf{Application 2 (Runtime Keyboard Engine):} Contains a Setup and Command Mapper GUI (Component A) to configure key-to-command mappings and choose a camera stream, and a Background Vision Watch Engine (Component B) that tracks AprilTag homography $H$, extracts MediaPipe hand landmarks, performs scale normalization ($L_{\text{hand}}$), evaluates a 12~FPS 5-frame sliding window with PyTorch LSTM on CPU, transforms coordinates ($P_{\text{XML}} = H \cdot P_{\text{pixel}}$), and dispatches key commands.
\end{itemize}

\subsection{Architectural Design Patterns Applied}
\label{subsec:req_design_patterns}
The software design uses standard design patterns to keep the code modular and maintainable:
\begin{enumerate}
    \item \textbf{Model-View-Controller (MVC):} Used in the Layout Designer (\texttt{designer\_app.py}) to separate the visual canvas (View) from the XML coordinate data (Model) and user mouse actions (Controller).
    \item \textbf{Producer-Consumer Thread Queue:} Used in Application 2 to buffer webcam frames captured by \texttt{camera\_thread.py} into a thread-safe Queue read by the model manager (\texttt{model\_manager.py}), avoiding dropped video frames.
    \item \textbf{Strategy Pattern for Action Dispatching:} Separates regular keyboard typing from shell script execution into modular command handlers.
    \item \textbf{Singleton Model Manager:} Ensures the trained PyTorch touch model (\texttt{best\_finger\_touch\_lstm.pth}) is loaded into memory only once during startup.
\end{enumerate}

\textbf{FR-07} & Keystroke Action Mapping & Setup GUI must enable users to map key IDs to single keystrokes (e.g., `'A'`, `'Space'`, `'Enter'`). \\
\textbf{FR-08} & System Command Mapping & Setup GUI must enable users to map key IDs to executable system shell commands or external Python scripts. \\
\textbf{FR-09} & Action Profile Multiplexing & System must allow users to save, load, and switch between multiple distinct action combination profiles (JSON/XML) for the exact same physical printed layout sheet without reprinting the paper. \\
\textbf{FR-10} & Multi-Threaded Video Capture & Runtime engine must run OpenCV frame acquisition in a dedicated background thread to prevent frame drops. \\
\textbf{FR-11} & AprilTag Sub-Pixel Tracking & AprilTag tracker engine must detect tag quads and extract sub-pixel corner coordinates under perspective camera tilt. \\
\textbf{FR-12} & SVD Homography Solver & Engine must compute the $3 \times 3$ Planar Homography matrix $H$ using SVD ($\mathbf{A} \mathbf{h} = \mathbf{0}$) from tracked AprilTag correspondences. \\
\textbf{FR-13} & MediaPipe 21 Joint Pose & Engine must regress 2D pixel coordinates for 21 anatomical hand joint keypoints of the active interacting hand (\texttt{num\_hands=1}) per video frame. \\
\textbf{FR-14} & Unitless Hand Scale Norm & System must translate keypoints to wrist origin $\mathbf{P}_0$ and scale coordinates by middle MCP hand length $L_{\text{hand}} = \|\mathbf{P}_9 - \mathbf{P}_0\|_2$. \\
\textbf{FR-15} & Direct Raw Propagation & Feature pipeline must propagate scale-normalized coordinates directly to classifier without artificial temporal low-pass smoothing. \\
\textbf{FR-16} & 5-Frame Window Generation & System must assemble 84-dimensional feature vectors into sliding windows of 5 frames with 2-frame overlap (stride of 3 frames) at 12~FPS representing the active single hand. \\
\textbf{FR-17} & PyTorch LSTM Touch Inference & Lightweight PyTorch model (\texttt{best\_finger\_touch\_lstm.pth}) must classify active finger paper touch contact probability ($P > 0.90$) across all 5 digits on standard CPU. \\
\textbf{FR-18} & Planar Coordinate Mapping & Engine must map active fingertip pixel coordinates through $H$ into XML layout space ($\mathbf{P}_{\text{XML}} = H \cdot \mathbf{P}_{\text{pixel}}$) and execute action. \\
\bottomrule
\end{tabular}%
\end{table}

\subsection{Detailed Functional Requirements Subsection Breakdown}
\label{subsec:req_fr_details}
The 18 functional requirements are grouped into four main subsystem areas:
\begin{enumerate}
    \item \textbf{Layout Designer Domain (FR-01 to FR-04):} Implemented in Application 1 (\texttt{designer/designer\_app.py}). Ensures that creating buttons, calculating bounding boxes, placing AprilTag anchors, rendering vector PDFs, and writing XML layout files work smoothly for any custom keyboard layout.
    \item \textbf{Setup and Command Mapper Domain (FR-05 to FR-09):} Implemented in Application 2 Component A. Manages camera selection across standard and low resolutions, XML layout loading, custom keystroke and shell command assignments, and saving or loading profile files, allowing users to switch action combinations on the exact same printed paper sheet without reprinting.
    \item \textbf{Vision Perception and Scale Normalization Domain (FR-10 to FR-16):} Implemented in Application 2 Component B. Handles multi-threaded camera capture (\texttt{camera\_thread.py}), AprilTag tracking (\texttt{aprilTag/estimater.py}), MediaPipe single-hand joint tracking (\texttt{num\_hands=1}), hand length scale normalization ($L_{\text{hand}}$) with direct feature propagation, and 12~FPS 5-frame sliding window creation (\texttt{create\_windows.py}).
    \item \textbf{Touch Classification and Command Execution Domain (FR-17 to FR-18):} Implemented in Application 2 Component B. Manages CPU-based PyTorch LSTM touch inference (\texttt{best\_finger\_touch\_lstm.pth}) for all 5 digits of the active hand, planar homography coordinate mapping ($P_{\text{XML}} = H \cdot P_{\text{pixel}}$), XML key detection, and keystroke or shell command triggering.
\end{enumerate}

\subsection{Detailed Non-Functional Quality Constraints}
\label{subsec:req_nfr_details}
The 10 non-functional requirements set key operational targets:
\begin{itemize}
    \item \textbf{Performance and Real-Time Execution (NFR-01, NFR-06):} The system provides an end-to-end frame processing time of under $30$~ms (well within the 12~FPS budget of $83.3$~ms) on standard commodity CPUs without requiring a dedicated GPU.
    \item \textbf{Touch Classification Accuracy (NFR-02):} The PyTorch LSTM model trained on 5-frame scale-normalized feature windows achieves an F1-score of $0.963$ across all five fingers.
    \item \textbf{Tracking Precision and Camera Tilt Support (NFR-03, NFR-04):} AprilTag corner tracking reaches sub-pixel accuracy ($0.038$~px), maintaining stable homography calculations under camera tilt angles up to $75^\circ$.
    \item \textbf{Data Privacy Protection (NFR-08):} The system processes video feeds locally in memory and deletes raw camera frames after extracting 2D joint coordinates, keeping only anonymized coordinate arrays ($(x_i^{\text{norm}}, y_i^{\text{norm}})$).
\end{itemize}
