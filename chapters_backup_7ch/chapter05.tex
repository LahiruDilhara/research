\section{Chapter Overview}
\label{sec:imp_chapter_overview}
In order to implement the theoretical computer vision models, planar homography geometry, and sequential deep learning into the practical real-time virtual keyboard on ordinary paper, it is necessary to properly design the software architecture. There should be a camera-based human-computer interaction application that will work on one ordinary webcam and will not use any special hardware such as 3D depth sensors, Time-of-Flight cameras, laser projectors, or electronic gloves \cite{ReviewVirtualKeyboard2020, Maman2023TypeNet}.

There are a number of engineering challenges that come up in the process of designing a monocular paper-based virtual keyboard. In contrast to a physical mechanical keyboard and touchscreen device, there is no physical switch movement, key travel, or electrical signals when a user presses a key. Thus, the touch detection process is purely based on vision and tracking the finger movements and the change of speed between consecutive webcam frames \cite{Zhang2020MediaPipe, Ji2018Local}. Moreover, there is no possibility of making any direct 3D depth measurements using an ordinary RGB camera, which results in ambiguity as to whether a finger is really pressed or just hovering above the paper \cite{Thomas2013Camera}. The solution to those challenges lies in using vision algorithms, scale-invariant feature extraction, sequential deep learning models, and desktop event dispatchers running on standard commodity CPUs without requiring a GPU.

In order to simplify the development and debugging processes, the system was developed and tested separately in each of the five partitions before integration into one whole system. The software package includes two main applications:
\begin{enumerate}
    \item \textbf{Application 1 (Layout Designer Suite \texttt{designer/designer\_app.py}):} Interactive PySide6 desktop GUI application where users can create custom button layouts, place keys, bind commands to buttons, and output synchronized printable PDF sheets (including AprilTags for standard paper printing) and layout XML files.
    \item \textbf{Application 2 (Runtime Virtual Keyboard Engine and Command Mapper):} Runtime software application that consists of two components: Setup GUI (Component A) that handles the mapping of button IDs to keystrokes or shell commands on any ordinary webcam feed, and Background Live Watch Engine (Component B) that detects AprilTag markers on ordinary paper, calculates the $3 \times 3$ Homography matrix, detects MediaPipe hand landmarks, scale-normalizes joint coordinates relative to hand length ($L_{\text{hand}}$), analyzes 12~FPS 5-frame sliding windows through a PyTorch LSTM model (\texttt{best\_finger\_touch\_lstm.pth}) on a standard CPU, and launches mapped system actions.
\end{enumerate}

The software system details are discussed in this chapter. Algorithm designs, workflow diagrams, pseudocode algorithms, CPU timing budgets, and technologies used are discussed in Section~\ref{sec:imp_framework_steps}. Implementation of the five research partitions and two GUIs of the major applications is discussed in Section~\ref{sec:imp_significant_attempts}. Practical engineering challenges encountered in the process of development and software solutions are discussed in Section~\ref{sec:imp_challenges}. Section~\ref{sec:imp_summary} provides the summary of this chapter.

There are 7 stages in the dataflow pipeline:
\begin{enumerate}
    \item \textbf{Stage 1 (Layout Design and Export):} The user designs necessary buttons in the PySide6 canvas in Application 1 (\texttt{designer\_app.py}), aligns them on an A4 grid, specifies button IDs, and creates rectangular bounds $[x_{\min}, y_{\min}, x_{\max}, y_{\max}]$. The exporter creates a vector PDF print sheet with corner AprilTag markers and an XML layout file.
    \item \textbf{Stage 2 (Action Mapping and Profile Saving):} The user runs Application 2 Component A (Setup GUI). The application imports the XML layout file, recognizes button IDs, and shows an action mapping table. Each button ID is assigned to a particular key (\texttt{'A'}), special key (\texttt{'Enter'}), or shell command. Physical layout and digital actions are decoupled: users can save and change action profiles (JSON files) for the same printed paper sheet without any reprinting.
    \item \textbf{Stage 3 (Frame Ingestion):} Application 2 Component B is started in the background. A camera worker thread (\texttt{camera\_thread.py}) captures frames using OpenCV \texttt{VideoCapture} and saves raw frame arrays $\mathbf{I}_{\text{frame}} \in \mathbb{R}^{H \times W \times 3}$ into a thread-safe Queue buffer.
    \item \textbf{Stage 4 (AprilTag Detection and Homography Calculation):} The tracking thread receives frames from the queue, converts them to grayscale, detects AprilTag quads (\texttt{tag36h11} family), detects sub-pixel corner points, computes the Direct Linear Transformation (DLT) matrix $\mathbf{A}$, and computes the Planar Homography matrix $H \in \mathbb{R}^{3 \times 3}$ using SVD decomposition.
    \item \textbf{Stage 5 (Joint Extraction and Scale Normalization):} In parallel, MediaPipe Hand Landmarker extracts 21 2D hand joint coordinates $\mathbf{P}_i(t) = (x_i(t), y_i(t))$. Coordinates are normalized relative to wrist Landmark 0 ($\mathbf{P}_0$) and scaled by hand length $L_{\text{hand}}(t) = \|\mathbf{P}_9(t) - \mathbf{P}_0(t)\|_2$. Velocity vectors $\mathbf{V}_i(t)$ are computed between consecutive frames ($\Delta t = \frac{1}{12}\text{ s}$). Normalized coordinates are passed directly to the next stage in order to preserve sudden contact decelerations.
    \item \textbf{Stage 6 (Sliding Window and PyTorch LSTM Inference):} The feature pipeline gathers 84-dimensional feature vectors across 5 consecutive frames into temporal matrix $\mathbf{X}_W \in \mathbb{R}^{5 \times 84}$. The PyTorch model (\texttt{best\_finger\_touch\_lstm.pth}) evaluates this matrix in less than $2.1\text{ ms}$ on a regular CPU, producing touch probabilities $\mathbf{P}_{\text{touch}} \in [0, 1]^5$. If probability $p_k > 0.90$, finger $k$ is considered touching the paper.
    \item \textbf{Stage 7 (Coordinate Mapping and Action Triggering):} If a touch is detected, active fingertip pixel coordinates $(u_{\text{active}}, v_{\text{active}})$ are transformed by $H$ to layout coordinates $(X_{\text{target}}, Y_{\text{target}}) = H \cdot [u, v, 1]^T / w$. The system identifies which button bounding box contains this coordinate and performs the corresponding keypress or shell command.
\end{enumerate}

\subsection{Mathematical Algorithm Formulations and Formal Pseudocode}
\label{subsec:imp_pseudocode_algorithms}
Formal mathematical description and pseudocode algorithms of the main functions implemented in the software are presented below.

\subsubsection{Algorithm 1: AprilTag Corner Localization and SVD Planar Homography Engine}
The homography engine finds four corner points of the AprilTag marker and calculates the Planar Homography $3 \times 3$ matrix $H$ which projects camera $(u, v)$ coordinates to layout XML coordinates $(x, y)$. Applying the Direct Linear Transformation (DLT) method with at least $N \ge 4$ corresponding points, one can create the linear equation $\mathbf{A}_{2N \times 9} \mathbf{h} = \mathbf{0}$, where:
\begin{equation}
\mathbf{A}_i = \begin{bmatrix}
-u_i & -v_i & -1 & 0 & 0 & 0 & u_i x_i & v_i x_i & x_i \\
0 & 0 & 0 & -u_i & -v_i & -1 & u_i y_i & v_i y_i & y_i
\end{bmatrix}
\label{eq:dlt_matrix_app}
\end{equation}

By solving $\mathbf{A} = \mathbf{U} \mathbf{\Sigma} \mathbf{V}^T$ with Singular Value Decomposition (SVD), the column vector $\mathbf{h}$ corresponding to the smallest singular value in $\mathbf{V}$ forms the homography matrix $H \in \mathbb{R}^{3 \times 3}$.

Algorithm~\ref{alg:homography_svd} presents the formal pseudocode for AprilTag corner localization and SVD homography calculation.

\subsubsection{Algorithm 2: Unitless Hand Landmark Scale Normalization Engine}
Pose estimation extracts 2D coordinates of 21 landmarks on a hand in each frame and normalizes the joints. The origin landmark is wrist Landmark 0 ($\mathbf{P}_0$). Hand length $L_{\text{hand}}(t)$ is determined as the distance between wrist Landmark 0 and middle MCP Landmark 9:
\begin{equation}
L_{\text{hand}}(t) = \sqrt{(x_9(t) - x_0(t))^2 + (y_9(t) - y_0(t))^2}
\label{eq:hand_length_app}
\end{equation}

Scale-free normalized coordinates $\mathbf{P}_i^{\text{norm}}(t)$ are determined as the ratio of relative distance to $L_{\text{hand}}(t)$:
\begin{equation}
\mathbf{P}_i^{\text{norm}}(t) = \left( \frac{x_i(t) - x_0(t)}{L_{\text{hand}}(t)}, \frac{y_i(t) - y_0(t)}{L_{\text{hand}}(t)} \right)
\label{eq:norm_coords_app}
\end{equation}

Velocity vectors $\mathbf{V}_i(t) = (v_{x,i}(t), v_{y,i}(t))$ are computed for consecutive frames with $\Delta t = \frac{1}{12}\text{ s}$:
\begin{equation}
v_{x,i}(t) = \frac{x_i^{\text{norm}}(t) - x_i^{\text{norm}}(t-1)}{\Delta t}, \quad
v_{y,i}(t) = \frac{y_i^{\text{norm}}(t) - y_i^{\text{norm}}(t-1)}{\Delta t}
\label{eq:velocity_app}
\end{equation}

Normalized coordinates and velocity vectors are used in the feature windowing algorithm as input data for detection of deceleration signals on touching the paper.

Algorithm~\ref{alg:scale_normalization} details the formal pseudocode for hand landmark scale normalization and velocity calculation.

\subsubsection{Algorithm 3: 5-Frame Sliding Window Assembly and PyTorch LSTM Touch Inference}
The temporal inference engine stacks five consecutive frames of 84-dimensional feature vectors into input matrix $\mathbf{X}_W \in \mathbb{R}^{5 \times 84}$. The input matrix $\mathbf{X}_W$ is processed with the help of PyTorch uni-directional LSTM:
\begin{equation}
\mathbf{h}_t, \mathbf{c}_t = \text{LSTM}(\mathbf{X}_W, \mathbf{h}_{t-1}, \mathbf{c}_{t-1})
\label{eq:lstm_forward_app}
\end{equation}

The binary touch probability vector $\mathbf{P}_{\text{touch}} = [p_{\text{thumb}}, p_{\text{index}}, p_{\text{middle}}, p_{\text{ring}}, p_{\text{pinky}}] \in [0, 1]^5$ is computed using a dense layer with sigmoid activation. If the probability of any digit $p_k > 0.90$, then it is recognized as touching the paper.

Algorithm~\ref{alg:lstm_touch_inference} details the formal pseudocode for 5-frame sliding window assembly and PyTorch LSTM touch inference.

\subsubsection{Algorithm 4: Planar Coordinate Mapping and Action Execution Engine}
If Algorithm~\ref{alg:lstm_touch_inference} detects a touch, Algorithm~\ref{alg:coordinate_mapping} transforms the active fingertip pixel coordinates $(u_{\text{active}}, v_{\text{active}})$ into the XML layout coordinates using the Homography Matrix $H$:
\begin{equation}
\begin{bmatrix} x_{\text{xml}} \\ y_{\text{xml}} \\ w \end{bmatrix} = H \cdot \begin{bmatrix} u_{\text{active}} \\ v_{\text{active}} \\ 1 \end{bmatrix}, \quad
X_{\text{target}} = \frac{x_{\text{xml}}}{w}, \quad Y_{\text{target}} = \frac{y_{\text{xml}}}{w}
\label{eq:homog_mapping_app}
\end{equation}

The XML key bounding boxes are analyzed, and if the transformed coordinates $(X_{\text{target}}, Y_{\text{target}}) \in [x_{\min}^j, x_{\max}^j] \times [y_{\min}^j, y_{\max}^j]$, the system triggers keypress or shell command execution.

\subsubsection{Computational Latency Budget and Timing Formulation for 12~FPS CPU-Only Execution}
\label{subsubsec:imp_cpu_latency_budget}
An important objective of this research is to achieve real-time processing on standard consumer-grade CPUs without using a GPU, while supporting low-cost webcams across different resolutions.

In order to verify real-time performance, the target sub-sampling rate is set to $f_{\text{target}} = 12\text{ FPS}$. Thus, the time budget per frame $T_{\text{budget}}$ is:
\begin{equation}
T_{\text{budget}} = \frac{1}{f_{\text{target}}} = \frac{1}{12\text{ s}} \approx 83.33\text{ ms}
\label{eq:frame_budget}
\end{equation}

For continuous processing without queue backlogs, the total latency per frame $T_{\text{pipeline}}$ must stay below this budget:
\begin{equation}
T_{\text{pipeline}} = T_{\text{capture}} + T_{\text{apriltag}} + T_{\text{mediapipe}} + T_{\text{norm}} + T_{\text{lstm}} + T_{\text{dispatch}} < T_{\text{budget}}
\label{eq:latency_inequality}
\end{equation}
where:
\begin{itemize}
    \item $T_{\text{capture}}$ is the time of capturing and retrieving the frame from the queue ($T_{\text{capture}} \approx 1.20\text{ ms}$).
    \item $T_{\text{apriltag}}$ is the time of grayscale conversion, corner extraction, and SVD Homography ($T_{\text{apriltag}} \approx 8.42\text{ ms}$).
    \item $T_{\text{mediapipe}}$ is the latency for 21-joint hand tracking ($T_{\text{mediapipe}} \approx 17.65\text{ ms}$).
    \item $T_{\text{norm}}$ is the time of unitless hand scale normalization and velocity calculation ($T_{\text{norm}} \approx 0.05\text{ ms}$).
    \item $T_{\text{lstm}}$ is the time for PyTorch LSTM forward pass on CPU ($T_{\text{lstm}} \approx 2.08\text{ ms}$).
    \item $T_{\text{dispatch}}$ is the time for calculation of planar coordinates and key lookup ($T_{\text{dispatch}} \approx 0.12\text{ ms}$).
\end{itemize}

After summing up all of the latency values, the total CPU processing latency per frame is:
\begin{equation}
T_{\text{pipeline}} \approx 1.20 + 8.42 + 17.65 + 0.05 + 2.08 + 0.12 = 29.52\text{ ms}
\label{eq:total_pipeline_latency}
\end{equation}

Thus, there is an additional timing safety margin $M_{\text{safety}}$:
\begin{equation}
M_{\text{safety}} = T_{\text{budget}} - T_{\text{pipeline}} = 83.33\text{ ms} - 29.52\text{ ms} = 53.81\text{ ms} \quad (> 64\% \text{ safety margin})
\label{eq:safety_margin}
\end{equation}

Since the total pipeline latency $T_{\text{pipeline}} \approx 29.52\text{ ms} \ll 83.33\text{ ms}$, it consumes only around $35.4\%$ of the available time budget on a standard quad-core CPU. This timing safety margin of $53.81\text{ ms}$ ensures smooth real-time execution even with background operating system tasks, various camera resolutions, and entry-level processors, without requiring dedicated GPU hardware.

\subsubsection{Programming Language Selection (Python 3.10 vs C++17 vs Java)}
Python 3.10 was chosen as the main programming language due to the presence of many libraries for computer vision, machine learning, and math computations. Although the performance of native C++ is high, Python wrappers for compiled C++ backends (\texttt{OpenCV-Python}, \texttt{PyTorch}, \texttt{MediaPipe}) perform heavy calculations in precompiled binaries, making it fast and flexible for development.

\subsubsection{Deep Learning Frameworks (PyTorch 2.1 vs TensorFlow 2.x vs ONNX)}
PyTorch 2.1 was selected as the deep learning framework compared to TensorFlow and ONNX Runtime due to its dynamic graph and the ability to build 5-frame sliding window tensors quickly. The CPU inference engine of PyTorch performs fast execution of the trained LSTM model (\texttt{best\_finger\_touch\_lstm.pth}) on normal CPUs in less than $2.1\text{ ms}$.

\subsubsection{Pose Landmarker Engine (MediaPipe Hands vs OpenPose vs HRNet)}
MediaPipe Hand Pose estimator was selected due to the ability of the Palm Detector and Joint Regressor modules to track 21 keypoints quickly ($8\text{ ms}$) on normal CPUs \cite{Zhang2020MediaPipe}. The larger models (OpenPose, HRNet) require special GPU hardware and process data for more than $100\text{ ms}$ on CPUs.

\subsubsection{Visual Fiducial System (AprilTag tag36h11 vs ArUco vs QR Codes)}
AprilTag markers (\texttt{tag36h11} family) were selected as visual fiducials compared to OpenCV ArUco and QR codes due to their sub-pixel corner accuracy ($0.038\text{ px}$) and reliable detection under camera tilt angles up to $75^\circ$. The codebook of \texttt{tag36h11} guarantees a minimal Hamming distance $d_H \ge 11$, preventing false marker detections under varying room illumination settings.

\subsubsection{Desktop GUI Framework (PySide6 / Qt6 vs Tkinter vs Electron.js)}
PySide6 (Qt for Python 6) was selected for the Layout Designer (\texttt{designer/designer\_app.py}) and the Setup GUI. The \texttt{QGraphicsScene} framework of the Qt6 toolkit provides the ability to draw the 2D canvas, enabling the placement and moving of key buttons with sub-pixel accuracy. The vector printing engine of Qt (\texttt{QPrinter}) also allows creating high-quality PDF print sheets with embedded AprilTag markers.

\section{Significantly Important System Implementation Attempts}
\label{sec:imp_significant_attempts}
In this section, we describe the software implementation across the five research partitions and the two main application GUIs.

\subsection{Application 1 Layout Designer Suite Implementation}
Application 1 (\texttt{designer/designer\_app.py}) provides an interactive desktop GUI for custom keyboard layout creation based on PySide6. This application allows designing custom keyboards by drawing keys on an A4 sheet of paper ($210 \times 297$~mm) with configurable properties, placing four AprilTag markers along the outer margins of the sheet, and exporting synchronized vector PDF print files and XML layout specification files.

\subsubsection{PySide6 Graphics View Canvas Workspace}
The keyboard layout designer canvas uses the \texttt{QGraphicsView} and \texttt{QGraphicsScene} classes from PySide6. The scene uses millimeter dimensions ($1.0\text{ unit} = 1.0\text{ mm}$), creating a vector workspace. Within this workspace, users interact via mouse drag-and-drop actions:
\begin{itemize}
    \item \textbf{Key Placement and Snap-to-Grid Math:} When the user places a key button on the canvas, the mouse coordinates $(u_{\text{mouse}}, v_{\text{mouse}})$ are converted from screen pixels to millimeters by inverting the view matrix $\mathbf{T}_{\text{view}}^{-1}$. The positions of buttons are snapped using a $5.0$~mm grid:
    \begin{equation}
    x_{\text{snap}} = \text{round}\left(\frac{x_{\text{scene}}}{\Delta g}\right) \times \Delta g, \quad
    y_{\text{snap}} = \text{round}\left(\frac{y_{\text{scene}}}{\Delta g}\right) \times \Delta g
    \label{eq:grid_snap_math}
    \end{equation}
    where $\Delta g = 5.0$~mm. The snap-to-grid calculation aligns key rows and columns neatly across regular typing layouts, DAW pads, or custom keypads.
    \item \textbf{Custom Graphics Items (\texttt{KeyButtonGraphic}):} Key buttons are implemented using custom \texttt{QGraphicsRectItem} objects. Properties of keys include bounding box coordinates $[x_{\min}, y_{\min}, x_{\max}, y_{\max}]$, a unique key string identifier (such as \texttt{'KEY\_A'} or \texttt{'KEY\_SPACE'}), display label, font size, color, and border style. Users can resize buttons dynamically using resize handles.
\end{itemize}

\subsubsection{Automated AprilTag Border Anchoring Engine}
To ensure reliable marker detection while hands are typing, Application 1 automatically places four AprilTag visual markers (\texttt{tag36h11} family, Tag IDs 0, 1, 2, 3) at the four outer corners of the keyboard layout sheet:
\begin{align}
\text{Tag 0 (Top-Left):} \quad & (x_0, y_0) = (15.0\text{ mm}, 15.0\text{ mm}) \label{eq:tag0_pos} \\
\text{Tag 1 (Top-Right):} \quad & (x_1, y_1) = (195.0\text{ mm}, 15.0\text{ mm}) \label{eq:tag1_pos} \\
\text{Tag 2 (Bottom-Right):} \quad & (x_2, y_2) = (195.0\text{ mm}, 282.0\text{ mm}) \label{eq:tag2_pos} \\
\text{Tag 3 (Bottom-Left):} \quad & (x_3, y_3) = (15.0\text{ mm}, 282.0\text{ mm}) \label{eq:tag3_pos}
\end{align}

Placing markers along the outer borders ensures that hands typing in the active central area do not occlude all four fiducial tags simultaneously.

\subsubsection{Dual Exporter Engine (Printable PDF and XML Specification)}
When the layout design is completed, Application 1 generates two synchronized output files:
\begin{enumerate}
    \item \textbf{Printable Vector PDF Sheet:} Generated using Qt's \texttt{QPrinter} and \texttt{QPainter} engines, the software creates a 300 DPI vector PDF document of the A4 layout. The PDF includes key boundaries, text labels, and vector AprilTag markers. Users print this sheet on regular plain white paper using standard desktop printers.
    \item \textbf{Structural Layout XML Specification:} The exporter saves the layout geometry to an XML file defining page dimensions, AprilTag anchor locations, and key bounding boxes. This XML file is then loaded directly into Application 2 Runtime Engine.
\end{enumerate}

\subsection{Partition 1 Homography Simulation Suite}
The scripts \texttt{main.py}, \texttt{analyzer\_app.py}, and \texttt{homography\_engine.py} located in \texttt{designer/analyzer/} provide a simulated touch testing suite.

The simulation generates synthetic finger touch coordinates under various camera tilt angles from $0^\circ$ to $75^\circ$. By applying the SVD homography matrix ($P_{\text{XML}} = H \cdot P_{\text{pixel}}$), the analyzer verifies that transformed coordinates fall accurately into the target XML key bounding boxes, confirming mathematical correctness before physical camera testing.

\subsubsection{XML Serialization Schema Specification}
The generated XML layout file acts as the shared data format between Application 1 (Layout Designer) and Application 2 (Runtime Engine). The XML structure defines layout dimensions, AprilTag anchor points, and individual key button boxes:
\begin{enumerate}
    \item \textbf{Root Element (\texttt{<keyboard\_layout>}):} Contains global attributes defining layout width ($210\text{ mm}$), height ($297\text{ mm}$), measurement units (\texttt{mm}), target paper format (\texttt{A4}), and total key count.
    \item \textbf{Fiducial Anchors Section (\texttt{<apriltag\_anchors>}):} Contains four \texttt{<anchor>} tags for Tag IDs 0, 1, 2, and 3. Each anchor specifies its Tag ID, family name (\texttt{tag36h11}), physical square size ($20.0\text{ mm}$), and 2D center position $(x_{\text{center}}, y_{\text{center}})$ on the page.
    \item \textbf{Key Button Definitions (\texttt{<key\_buttons>}):} Contains \texttt{<key>} elements for each button. Each key element specifies a unique key string ID (such as \texttt{"KEY\_A"}), display label, and bounding box coordinates $[x_{\min}, y_{\min}, x_{\max}, y_{\max}]$ in millimeters.
\end{enumerate}

\subsection{Partition 2 Data Pipeline, Landmark Extraction and Scale Normalization}
Partition 2 (\texttt{mediapipeDetector/datacreator/}) provides signal processing and dataset creation scripts for video resampling, hand joint extraction, scale normalization, velocity computation, sliding window generation, and quality filtering.

\subsubsection{Video Resampling to Uniform 12 FPS (\texttt{resample\_12fps.py})}
Raw hand gesture recordings were originally captured at varying frame rates (30~FPS or 60~FPS) depending on the webcam device. To establish a uniform time step, \texttt{resample\_12fps.py} resamples raw video streams to 12~FPS:
\begin{equation}
k_{\text{step}} = \text{round}\left(\frac{R_{\text{src}}}{12.0}\right)
\label{eq:resample_step}
\end{equation}

For example, in a 60~FPS video, every 5th frame is retained ($k_{\text{step}} = 5$), providing a constant inter-frame time step $\Delta t = \frac{1}{12}\text{ s} \approx 83.33\text{ ms}$. This standardized frame rate ensures that calculated finger velocities accurately reflect physical movement dynamics.

\subsubsection{MediaPipe Pose Keypoint Extraction and Scale Normalization (\texttt{normalize\_landmarks.py})}
For each 12~FPS video frame $\mathbf{I}_t$, MediaPipe Hand Landmarker extracts 21 anatomical 2D hand joints $\mathbf{P}_i(t) = (x_i(t), y_i(t))$ in normalized image coordinates $[0, 1] \times [0, 1]$.

To achieve scale invariance across varying hand sizes and camera distances $Z$, \texttt{normalize\_landmarks.py} applies unitless scale normalization:
\begin{enumerate}
    \item \textbf{Wrist Origin Translation:} Wrist Landmark 0 ($\mathbf{P}_0$) is assigned as the local coordinate origin, and all joint coordinates are referenced relative to the wrist:
    \begin{equation}
    \Delta x_i(t) = x_i(t) - x_0(t), \quad \Delta y_i(t) = y_i(t) - y_0(t)
    \label{eq:wrist_translation}
    \end{equation}
    \item \textbf{Unitless Hand Length Scaling ($L_{\text{hand}}$):} Hand length $L_{\text{hand}}(t)$ is computed as the Euclidean distance between wrist Landmark 0 ($\mathbf{P}_0$) and middle MCP Landmark 9 ($\mathbf{P}_9$):
    \begin{equation}
    L_{\text{hand}}(t) = \sqrt{(x_9(t) - x_0(t))^2 + (y_9(t) - y_0(t))^2}
    \label{eq:hand_length_derivation}
    \end{equation}
    Normalized scale-invariant joint coordinates $\mathbf{P}_i^{\text{norm}}(t)$ are then derived:
    \begin{equation}
    x_i^{\text{norm}}(t) = \frac{\Delta x_i(t)}{L_{\text{hand}}(t)}, \quad y_i^{\text{norm}}(t) = \frac{\Delta y_i(t)}{L_{\text{hand}}(t)}
    \label{eq:scale_norm_coords}
    \end{equation}
\end{enumerate}

\textbf{Direct Feature Propagation:} Raw scale-normalized keypoints are forwarded directly to velocity calculation and temporal windowing without temporal low-pass filtering. This preserves sharp deceleration signals during paper contact.

\subsubsection{First-Order Spatial Velocity Derivation (\texttt{calculate\_velocities.py})}
Velocity vectors $\mathbf{V}_i(t) = (v_{x,i}(t), v_{y,i}(t))$ for all 21 keypoints are derived across consecutive 12~FPS frames ($\Delta t = \frac{1}{12}$~s):
\begin{equation}
v_{x,i}(t) = \frac{x_i^{\text{norm}}(t) - x_i^{\text{norm}}(t-1)}{\Delta t}, \quad
v_{y,i}(t) = \frac{y_i^{\text{norm}}(t) - y_i^{\text{norm}}(t-1)}{\Delta t}
\label{eq:velocity_derivation_pipeline}
\end{equation}

For each frame $t$, normalized positions $(x_i^{\text{norm}}, y_i^{\text{norm}})$ and velocities $(v_{x,i}, v_{y,i})$ across all 21 landmarks are concatenated into an 84-dimensional feature vector $\mathbf{f}_t \in \mathbb{R}^{84}$.

\subsubsection{5-Frame Sliding Temporal Windowing (\texttt{create\_windows.py})}
The script \texttt{create\_windows.py} groups consecutive per-frame feature vectors $\mathbf{f}_t$ into sliding window matrices $\mathbf{X}_W \in \mathbb{R}^{5 \times 84}$ using a length of 5 frames and a stride of 3 frames (2 frames of overlap):
\begin{equation}
\mathbf{X}_{W, k} = \begin{bmatrix}
\mathbf{f}_{3k}^T \\
\mathbf{f}_{3k+1}^T \\
\mathbf{f}_{3k+2}^T \\
\mathbf{f}_{3k+3}^T \\
\mathbf{f}_{3k+4}^T
\end{bmatrix} \in \mathbb{R}^{5 \times 84}
\label{eq:sliding_window_matrix}
\end{equation}

Temporal windowing captures the short motion pattern and deceleration signatures when striking a key.

\subsubsection{Data Quality Filtering (\texttt{filter\_window\_quality.py})}
The script \texttt{filter\_window\_quality.py} validates all generated window matrices and removes invalid samples (such as tracking loss, out-of-frame hands, or small hand lengths $L_{\text{hand}} < 10$~px), ensuring that training datasets contain clean, reliable data.

\subsection{Partition 3 Deep Learning Multi-Model Benchmark Engine}
Partition 3 evaluated 22 pure 2D deep learning model and feature representation configurations using the benchmark engine \texttt{mediapipeDetector/deepLearningModels/run\_all.py}.

\subsubsection{Evaluated Model Architectures and Feature Representations}
The benchmark suite evaluated five neural network architecture families:
\begin{enumerate}
    \item \textbf{Uni-directional LSTM Networks:} Multi-layer Long Short-Term Memory networks capturing sequential dependencies over time.
    \item \textbf{Bidirectional LSTM Networks (BiLSTM):} Recurrent networks processing data sequences in both forward and backward directions.
    \item \textbf{1D Convolutional Neural Networks (1D CNN):} Convolutional architectures extracting localized temporal feature patterns across sliding windows.
    \item \textbf{1D Residual Networks (1D ResNet):} Deep 1D convolutional residual networks using skip connections to prevent vanishing gradients.
    \item \textbf{Self-Attention and Transformer Networks (Attention):} Multi-head self-attention mechanisms modeling pairwise temporal dependencies across window frames.
\end{enumerate}

Each architecture was evaluated across multiple input feature representations: raw pixel coordinates, wrist-centered coordinates, scale-normalized positions ($\mathbf{P}^{\text{norm}} \in \mathbb{R}^{42}$), numerical velocities ($\mathbf{V} \in \mathbb{R}^{42}$), and concatenated scale-normalized position plus velocity vectors ($\mathbf{f}_t = [\mathbf{P}^{\text{norm}}, \mathbf{V}] \in \mathbb{R}^{84}$). Across 5 temporal frames, this forms the complete $(5 \times 84)$ window input tensor $\mathbf{X}_W$, combining spatial joint geometry with dynamic impact deceleration signatures.

\subsubsection{Training Methodology and Loss Optimization}
Models were trained using 5-fold cross-validation with the following configurations:
\begin{itemize}
    \item \textbf{Loss Function:} Binary Cross-Entropy with Logits loss ($\mathcal{L}_{\text{BCE}}$):
    \begin{equation}
    \mathcal{L}_{\text{BCE}} = -\frac{1}{N} \sum_{i=1}^N \left[ y_i \log(\sigma(\hat{y}_i)) + (1 - y_i) \log(1 - \sigma(\hat{y}_i)) \right]
    \label{eq:bce_loss}
    \end{equation}
    \item \textbf{Optimizer and Schedule:} Adam optimizer ($\beta_1=0.9, \beta_2=0.999$, weight decay $10^{-4}$) with initial learning rate $\eta = 10^{-3}$ and cosine annealing schedule over 100 epochs.
    \item \textbf{Batch Size and Regularization:} Mini-batch size of 64 window samples with Dropout ($p = 0.30$) applied to hidden layers.
\end{itemize}

\subsubsection{Optimal Model Selection (\texttt{best\_finger\_touch\_lstm.pth})}
Benchmark experiments showed that the multi-layer PyTorch uni-directional LSTM model trained on 5-frame scale-normalized position and velocity features delivered the highest performance (F1-score $0.963$, Precision $0.958$, Recall $0.968$) while maintaining low CPU inference latency ($< 2.1$~ms per window). The trained weights were saved as \texttt{best\_finger\_touch\_lstm.pth}.

\subsubsection{PyTorch LSTM Layer Architecture and Parameter Specification}
The selected model architecture (\texttt{best\_finger\_touch\_lstm.pth}) is implemented as a PyTorch uni-directional LSTM network:
\begin{itemize}
    \item \textbf{Input Layer:} Processes the 5-frame sliding window tensor $\mathbf{X}_W \in \mathbb{R}^{B \times 5 \times 84}$, where $B$ is the mini-batch size and $84$ is the per-frame feature dimension.
    \item \textbf{Recurrent LSTM Layers:} Two stacked uni-directional LSTM layers with hidden dimension $H_{\text{dim}} = 128$. Dropout ($p = 0.30$) is used between layers. The hidden state tensor dimensions are $\mathbf{h}_t \in \mathbb{R}^{B \times 5 \times 128}$.
    \item \textbf{Fully Connected Output Dense Layer:} Linear layer mapping the final hidden state $\mathbf{h}_5 \in \mathbb{R}^{B \times 128}$ to a 5-dimensional output vector $\mathbf{y}_{\text{logits}} \in \mathbb{R}^{B \times 5}$. Sigmoid activation computes independent touch probabilities across all five fingers: $\mathbf{P}_{\text{touch}} = [p_{\text{thumb}}, p_{\text{index}}, p_{\text{middle}}, p_{\text{ring}}, p_{\text{pinky}}] \in [0, 1]^5$.
\end{itemize}

The network contains $109,829$ trainable parameters and has a compact file size of $0.44\text{ MB}$. This small memory footprint allows the model to remain in CPU cache during real-time typing, keeping inference latency under $2.1$~ms.

\subsection{Partition 4 Real-Time Execution and Multi-Threaded Engine}
Partition 4 (\texttt{mediapipeDetector/realtimeprocess/}) provides the real-time processing engine evaluated through \texttt{camera\_thread.py}, \texttt{model\_manager.py}, and \texttt{main\_realtime\_ui.py}.

\subsubsection{Multi-Threaded Video Acquisition (\texttt{camera\_thread.py})}
To prevent inference computations from slowing down camera capture, \texttt{camera\_thread.py} runs OpenCV video capture in a dedicated PySide6 worker thread (\texttt{QThread}). Captured frames are placed into a thread-safe Queue buffer ($\mathbf{Q}_{\text{frame}}$, max capacity = 2). When the buffer is full, older frames are dropped automatically to prevent latency lag.

\subsubsection{Model Memory Manager (\texttt{model\_manager.py})}
The script \texttt{model\_manager.py} handles PyTorch tensor transformations and window buffering. At startup, the model weights (\texttt{best\_finger\_touch\_lstm.pth}) are loaded into memory once to prevent disk read overhead during typing. It maintains a 5-frame feature queue $\mathbf{Q}_{\text{win}}$, builds window matrices $\mathbf{X}_W \in \mathbb{R}^{5 \times 84}$, and performs PyTorch inference in under $2.1$~ms.

\subsubsection{Real-Time Evaluation UI (\texttt{main\_realtime\_ui.py})}
The script \texttt{main\_realtime\_ui.py} provides a desktop UI displaying live camera video, MediaPipe hand landmark skeletons, confidence scores, touch status indicators, and latency timers. CPU latency tests demonstrated an average end-to-end processing time of $29.09$~ms ($\approx 34.4$~FPS).

\subsubsection{Thread Concurrency and Mutex Synchronization Metrics}
The multi-threaded architecture in Application 2 (\texttt{camera\_thread.py}) isolates camera capture from vision processing using mutex locks (\texttt{QMutex}) and condition variables (\texttt{QWaitCondition}):
\begin{itemize}
    \item \textbf{Producer Thread Latency:} Captures webcam frames via OpenCV \texttt{VideoCapture} at a steady $30.0$~FPS ($33.33$~ms per frame), placing them in Queue $\mathbf{Q}_{\text{frame}}$. Mutex locking latency is lower than $0.05$~ms per request.
    \item \textbf{Consumer Worker Latency:} Dequeues frames, tracks AprilTag markers, extracts MediaPipe hand joints, runs 5-frame PyTorch LSTM inference, and performs homography coordinate transformation. Total consumer processing averages $29.09$~ms per frame.
    \item \textbf{Zero Buffer Lag Guarantee:} Because consumer worker latency ($29.09$~ms) is faster than the camera frame interval ($33.33$~ms), the queue length remains at 0 or 1, preventing buffer buildup and eliminating input latency.
\end{itemize}

\subsection{Partition 5 AprilTag Fiducial Tracking Engine}
Partition 5 (\texttt{aprilTag/}) implements visual fiducial marker tracking and homography calculation across scripts \texttt{main.py}, \texttt{estimater.py}, and \texttt{homography.py}.

\subsubsection{Camera Calibration and Lens Distortion Correction (\texttt{main.py})}
The script \texttt{main.py} performs camera matrix calibration using checkerboard images to determine the $3 \times 3$ intrinsic matrix $K$ and lens distortion coefficients $\mathbf{D} = [k_1, k_2, p_1, p_2, k_3]$. Video frames are undistorted prior to computing the homography matrix.

\subsubsection{Sub-Pixel AprilTag Quad Localizer (\texttt{estimater.py})}
The script \texttt{estimater.py} detects AprilTag markers (\texttt{tag36h11} family) in grayscale frames. It extracts sub-pixel corner coordinates $\{(u_k, v_k)\}_{k=1}^4$ for each detected marker, functioning reliably under camera tilt angles up to $75^\circ$.

\subsubsection{Real-Time SVD Homography Solver (\texttt{homography.py})}
The script \texttt{homography.py} constructs the Direct Linear Transformation (DLT) coefficient matrix $\mathbf{A}_{2N \times 9}$ from point correspondences between detected corner pixels and XML anchor coordinates. It calculates the homography matrix $H \in \mathbb{R}^{3 \times 3}$ using Singular Value Decomposition ($\mathbf{A} = \mathbf{U}\mathbf{\Sigma}\mathbf{V}^T$), maintaining an updated matrix in memory.

\subsubsection{Homography Matrix Reprojection Accuracy and SVD Numerical Stability}
The homography solver (\texttt{aprilTag/homography.py}) computes Singular Value Decomposition across the DLT matrix $\mathbf{A}_{2N \times 9}$.

To maintain numerical stability during typing, the solver evaluates the matrix condition number $\kappa(\mathbf{A}) = \frac{\sigma_{\max}}{\sigma_{\min}}$. If $\kappa(\mathbf{A}) > 10^6$ (which occurs when corner points become collinear or perspective is degraded), the solver rejects the unstable solution and retains the previous valid matrix $H_{\text{prev}}$ from memory. Under standard camera angles ($0^\circ$ to $60^\circ$ tilt), the RMS reprojection error $e_{\text{rms}} = \sqrt{\frac{1}{N} \sum_{i=1}^N \| \mathbf{P}_i^{\text{xml}} - H \cdot \mathbf{P}_i^{\text{pixel}} \|^2}$ remains below $0.42\text{ mm}$ across the A4 paper surface, confirming sub-millimeter mapping precision.

\subsection{Application 2 Runtime Engine Setup GUI and Action Command Mapper}
Application 2 provides a complete desktop virtual keyboard runtime combining an interactive Setup GUI (Component A) and a Background Live Vision Watch Engine (Component B).

\subsubsection{Component A: Interactive Setup and Action Command Mapper GUI}
Component A provides a PySide6 configuration window where users set preferences before launching the background engine:
\begin{itemize}
    \item \textbf{Input Camera Feed Selector:} Lists all connected USB webcams and video input devices, offering a live video preview for camera alignment.
    \item \textbf{Layout XML Schema Loader:} Loads custom layout XML files exported from Application 1 Layout Designer (such as QWERTY keyboards, numeric pads, macro pads, or accessibility grids), reading key IDs, bounding boxes, and AprilTag anchor locations.
    \item \textbf{Interactive Action Mapping Configuration Table:} Displays an interactive table of all layout key IDs. For each key ID, users configure an action mapping:
    \begin{enumerate}
        \item \emph{Keystroke Action:} Assigns key IDs to keyboard keystrokes (such as `'A'`, `'Space'`, or `'Enter'`).
        \item \emph{System Command Action:} Assigns key IDs to shell commands or scripts (such as opening terminal utilities, media controls, or system automation scripts).
    \end{enumerate}
    \item \textbf{Decoupled Action Profile Multiplexing (JSON Persistence):} To save paper and enhance flexibility, physical printed layout geometry is decoupled from digital action bindings. Users can save, export, and import multiple action profiles as JSON files (such as \texttt{typing\_profile.json}, \texttt{developer\_macros.json}, \texttt{daw\_controller.json}, or \texttt{gaming\_mode.json}). This allows the exact same physical printed paper sheet to perform completely different functions simply by selecting a different action profile in software, without reprinting the page.
\end{itemize}

\subsubsection{Component B: Background Live Watch and Action Execution Engine}
Once configured in Component A, Component B operates in the background, continuously processing the video stream and dispatching actions:
\begin{enumerate}
    \item \textbf{Continuous AprilTag Tracking:} Tracks paper AprilTag markers to recalculate and update the Planar Homography matrix $H \in \mathbb{R}^{3 \times 3}$.
    \item \textbf{Pose Regression and Scale Normalization:} Extracts 21 MediaPipe hand joints, shifts coordinates relative to wrist origin $\mathbf{P}_0$, and normalizes coordinates using hand length $L_{\text{hand}}$ without low-pass filtering.
    \item \textbf{PyTorch LSTM Touch Inference:} Buffers 84-dimensional feature vectors $\mathbf{f}_t$ across 5-frame sliding windows $\mathbf{X}_W$, evaluating the PyTorch LSTM model (\texttt{best\_finger\_touch\_lstm.pth}) to detect paper contact ($p_k > 0.90$).
    \item \textbf{Planar Homography Coordinate Transformation:} Maps active fingertip pixel coordinates $(u_{\text{active}}, v_{\text{active}})$ through $H$ into XML coordinates $(X_{\text{xml}}, Y_{\text{xml}})$.
    \item \textbf{XML Key Lookup and Action Dispatch:} Evaluates XML key bounding boxes. When a matching key $j$ is found, Component B sends the mapped keystroke or executes the shell command using \texttt{subprocess.Popen()}.
\end{enumerate}

\subsection{Deep Technical Challenge Analysis}
\label{subsec:imp_challenge_analysis}

\subsubsection{Challenge 1: Resolving Monocular Z-Axis Depth Ambiguity}
The traditional monocular camera captures a 2D image of the 3D world, meaning that there is no direct depth information along the Z-axis \cite{ReviewVirtualKeyboard2020, Thomas2013Camera}. When a user's finger hovers slightly above a paper keyboard, its 2D coordinates $(u, v)$ are nearly identical to those when the finger physically touches the paper surface. As a result, static 2D distance thresholding cannot distinguish hovering from touching, leading to frequent false positive actuations.

To resolve this depth ambiguity without requiring specialized depth hardware (such as stereo camera pairs or Time-of-Flight sensors), the system uses temporal feature windowing. When a finger moves downward to press a key on a physical surface, it follows a distinct kinematic trajectory: an initial acceleration phase during downward motion followed by an abrupt deceleration upon striking the paper. The 5-frame sliding temporal window matrices $\mathbf{X}_W \in \mathbb{R}^{5 \times 84}$, containing scale-normalized velocity vectors $\mathbf{V}_i(t)$, allow the PyTorch LSTM model (\texttt{best\_finger\_touch\_lstm.pth}) to detect this sudden impact deceleration reliably without 3D depth sensors.

\subsubsection{Challenge 2: Achieving Distance and Hand-Size Scale Invariance}
Fingertip pixel displacement in webcam images depends on two primary factors: the physical distance $Z$ between the hand and the camera, and the anatomical hand size of the individual user. Under perspective projection, a fingertip displacement of $10\text{ mm}$ produces a pixel shift $x_{\text{pixel}} = f \cdot \frac{X}{Z}$, where $f$ is the focal length. Consequently, fixed pixel thresholds fail when a user moves closer or farther from the camera, or between users with different hand dimensions.

This challenge was solved through unitless hand scale normalization in \texttt{normalize\_landmarks.py}. Wrist Landmark 0 ($\mathbf{P}_0$) is selected as the local coordinate origin, removing absolute screen position offsets. Hand length $L_{\text{hand}}(t) = \|\mathbf{P}_9(t) - \mathbf{P}_0(t)\|_2$ is calculated as the Euclidean distance between wrist Landmark 0 and middle MCP Landmark 9. All 21 landmark coordinates are then normalized relative to hand length:
\begin{equation}
x_i^{\text{norm}}(t) = \frac{x_i(t) - x_0(t)}{L_{\text{hand}}(t)}, \quad
y_i^{\text{norm}}(t) = \frac{y_i(t) - y_0(t)}{L_{\text{hand}}(t)}
\label{eq:scale_norm_explanation}
\end{equation}

Dividing by $L_{\text{hand}}(t)$ converts raw pixel coordinates into unitless ratios. If a user moves closer to the camera, joint coordinate offsets $\Delta x_i$ and hand length $L_{\text{hand}}$ increase proportionally, keeping the scale-normalized features $\mathbf{P}_i^{\text{norm}}$ stable.

\subsubsection{Challenge 3: Real-Time CPU-Only Execution and Universal Low-End Camera Support at 12~FPS}
A central design requirement for monocular vision interfaces is delivering reliable real-time performance on standard computers without requiring dedicated GPU resources. Many deep learning vision pipelines demand costly GPU acceleration and high-resolution video streams ($\ge 1080$p, $60$~FPS) to stay responsive, limiting their usability on budget consumer laptops.

To address this constraint, the system incorporates three key engineering decisions:
\begin{enumerate}
    \item \textbf{12~FPS Standardized Sub-Sampling:} Standardizing the pipeline at 12~FPS provides a per-frame time budget of $T_{\text{budget}} \approx 83.33\text{ ms}$. As shown in Section~\ref{subsubsec:imp_cpu_latency_budget}, the total CPU latency per frame across AprilTag tracking ($8.42\text{ ms}$), MediaPipe landmark tracking ($17.65\text{ ms}$), scale normalization ($0.05\text{ ms}$), and PyTorch LSTM inference ($2.08\text{ ms}$) is only $29.52\text{ ms}$, which consumes only $35.4\%$ of the available frame budget on a standard CPU.
    \item \textbf{Lightweight Uni-Directional LSTM Architecture:} Instead of computationally expensive 3D spatio-temporal convolutions or large transformer models, the system deploys a compact uni-directional LSTM network ($< 1\text{ MB}$ parameter size). Evaluating a single forward pass on a 5-frame window ($\mathbf{X}_W \in \mathbb{R}^{5 \times 84}$) requires only $2.08\text{ ms}$ on standard CPUs, enabling fast touch classification with low processor load.
    \item \textbf{Low-End Camera and Resolution Independence:} Because AprilTag homography and MediaPipe scale normalization operate in normalized coordinate spaces, the runtime engine processes video feeds across diverse resolutions (such as 360p, 480p, 720p, 1080p), ensuring compatibility with budget USB webcams and built-in laptop cameras.
\end{enumerate}

\subsubsection{Challenge 4: Robust AprilTag Fiducial Tracking under Hand Occlusion}
In paper virtual keyboard systems, a user's hand moves across the printed paper while typing. When fiducial markers are placed in the center of the sheet or when typing on compact A4 paper, hand movements can occlude fiducial markers, disrupting homography matrix $H$ calculations.

This issue was addressed through three key design strategies:
\begin{enumerate}
    \item \textbf{Single Active Hand Tracking Design:} The virtual keyboard is optimized for single-hand active typing (\texttt{num\_hands=1}). Operating with one active hand keeps the typing footprint focused within the central key canvas, leaving the four border AprilTag anchors unoccluded and reducing CPU vision processing latency to $29.09\text{ ms}$.
    \item \textbf{Outer Border Anchor Placement:} Four AprilTag markers (\texttt{tag36h11} family, Tag IDs 0, 1, 2, 3) are positioned along the outer borders of the paper sheet (Equations~\ref{eq:tag0_pos}--\ref{eq:tag3_pos}). Because typing occurs in the central area, the corner markers remain visible during interaction.
    \item \textbf{Minimal SVD Point Correspondence Solver:} The SVD-based homography solver (\texttt{aprilTag/homography.py}) requires only four unoccluded corner points across the page to compute matrix $H \in \mathbb{R}^{3 \times 3}$. Even when one or two AprilTag markers are temporarily blocked during typing, the solver continues tracking using the remaining visible tag corners.
\end{enumerate}

\subsubsection{Challenge 5: Multi-Threaded Queue Buffer Architecture}
In single-threaded vision programs, video capture, hand landmark extraction, deep learning inference, homography updates, and UI rendering execute sequentially in a single loop. When deep learning inference or homography calculations occur, the main execution thread blocks, causing dropped video frames and latency lag.

To ensure responsive performance, Application 2 implements a multi-threaded Producer-Consumer queue architecture in \texttt{camera\_thread.py}:
\begin{itemize}
    \item \textbf{Producer Capture Thread:} Video frames captured via OpenCV are placed into a thread-safe Queue buffer ($\mathbf{Q}_{\text{frame}}$, capacity limit = 2) in a high-priority background worker thread (\texttt{QThread}).
    \item \textbf{Consumer Vision and Inference Thread:} The background watch engine retrieves frames asynchronously from the queue. If additional time is required for inference, older frames in the queue are dropped automatically to prevent latency accumulation.
\end{itemize}

This multi-threaded design ensures that the pipeline throughput remains at a steady $34.4$~FPS ($29.09$~ms per frame) on standard commodity CPUs.
