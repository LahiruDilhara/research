\section{Chapter Overview}
\label{sec:test_overview}
Evaluating a monocular paper virtual keyboard system requires practical testing across computer vision tracking, neural network touch classification, real-time processing speed, action triggering, and real user typing performance \cite{ReviewVirtualKeyboard2020, Maman2023TypeNet}. Unlike mechanical or touchscreen keyboards, a paper keyboard has no physical switches or electrical wiring. Therefore, the reliability of the system depends entirely on hand landmark tracking, scale-invariant feature extraction, temporal deep learning touch detection, and homography coordinate mapping under different conditions \cite{Zhang2020MediaPipe, Posner2012Single}.

Testing paper touch interfaces presents specific challenges. Because a standard webcam feed has no direct depth measurements, physical contact with the paper must be detected purely from 2D joint positions and speed changes over time \cite{Thomas2013Camera}. In addition, practical use requires the system to handle different user hand sizes, camera distances, and camera tilt angles, while maintaining near real-time performance at 12~FPS on standard commodity CPUs without requiring a GPU, across regular low-cost camera resolutions.

To evaluate the system thoroughly, tests were carried out across the two main application tools: Application 1 (Layout Designer \texttt{designer/designer\_app.py}) and Application 2 (Runtime Engine and Command Mapper). This chapter explains the testing plan, evaluation steps, benchmark results, and comparisons. Section~\ref{sec:test_plan_cases} presents the test plan with functional and non-functional test cases. Section~\ref{sec:test_workflow} outlines the evaluation process. Section~\ref{sec:test_results_review} presents the quantitative results for model architectures, window lengths, scale normalization, CPU execution at 12~FPS across camera resolutions, AprilTag homography tilt angles, latency breakdowns, and user typing speed. Finally, Section~\ref{sec:test_summary} summarizes the chapter.

\section{Testing and Evaluation Workflow}
\label{sec:test_workflow}
The testing process followed four main evaluation stages:
\begin{enumerate}
    \item \textbf{Stage 1 (Deep Learning Classifier Evaluation):} Evaluated 22 pure 2D model architecture combinations in \texttt{mediapipeDetector/}\linebreak[1]\texttt{deepLearningModels/}\linebreak[1]\texttt{run\_all.py} using 5-fold cross-validation, measuring Precision, Recall, F1-Score, and execution time.
    \item \textbf{Stage 2 (Feature and Window Ablation):} Tested different window lengths ($W \in \{1, 3, 5, 7, 9\}$), stride values, scale normalization ($L_{\text{hand}}$) versus raw features, and CPU execution speed across different video resolutions.
    \item \textbf{Stage 3 (Tracking and Homography Accuracy):} Evaluated AprilTag corner detection accuracy, sub-pixel fitting, and homography reprojection error across camera tilt angles from $0^\circ$ to $75^\circ$.
    \item \textbf{Stage 4 (Real-Time System Latency and User Typing Performance):} Measured end-to-end pipeline speed, component latency breakdowns, key hit detection rate, Words Per Minute (WPM), and Character Error Rate (CER) during typing tests with users.
\end{enumerate}

\subsubsection{Training Loss Convergence and Overfitting Analysis}
During 5-fold cross-validation of the PyTorch LSTM model (\texttt{best\allowbreak\_finger\allowbreak\_touch\allowbreak\_lstm.pth}), Binary Cross-Entropy loss ($\mathcal{L}_{\text{BCE}}$) was tracked across 100 epochs per fold.

\subsubsection{CPU Thread Memory Contention and Mutex Overhead Analysis}
Profiling Application 2 Component B showed that the multi-threaded queue design effectively isolates camera capture from deep learning inference. Mutex lock acquisition (\texttt{QMutex.lock()}) averaged $0.042$~ms per cycle, accounting for less than $0.15\%$ of the total pipeline latency.

Because PyTorch LSTM forward passes run on pre-allocated tensor memory, there was minimal memory contention between OpenCV frame decoding and PyTorch inference. No thread deadlocks or race conditions occurred during long testing runs.

\subsection{User Typing Performance and Character Error Rate Benchmark}
\label{subsec:test_user_typing}
User typing performance was tested with ten participants executing single-handed text transcription phrases on a printed A4 paper virtual keyboard. Testing single-hand typing matches the system scope, keeping camera marker visibility unobstructed and CPU latency low. Metrics included Words Per Minute (WPM) and Character Error Rate (CER):
\begin{equation}
\text{WPM} = \left( \frac{|C|}{5} \right) / T_{\text{min}}, \quad
\text{CER} = \left( \frac{S + D + I}{|R|} \right) \times 100\%
\label{eq:wpm_cer_formulas}
\end{equation}
where $|C|$ is total characters typed, $T_{\text{min}}$ is time in minutes, $S$ is substitutions, $D$ is deletions, $I$ is insertions, and $|R|$ is reference text length.

\section{Chapter Summary}
\label{sec:test_summary}
This chapter presented the empirical testing and evaluation results for the paper virtual keyboard system.

Section~\ref{sec:test_plan_cases} defined ten functional and seven non-functional test cases. Section~\ref{sec:test_workflow} described the evaluation workflow. Section~\ref{sec:test_results_review} presented quantitative benchmarks confirming that:
\begin{itemize}
    \item The uni-directional PyTorch LSTM model trained on normalized position and velocity features achieved an F1-score of $0.963$ with $2.08$~ms inference latency on CPU.
    \item Unitless scale normalization ($L_{\text{hand}}$) maintained distance invariance ($F1 \ge 0.958$) across camera distances from $30$~cm to $100$~cm.
    \item The 12~FPS standard architecture ran smoothly in real time on standard commodity CPUs without requiring a GPU, maintaining consistent touch classification accuracy ($F1 \approx 0.963$) across low-end and high-end video resolutions (360p to 1080p).
    \item AprilTag marker tracking maintained sub-millimeter reprojection accuracy ($e_{\text{rms}} \le 0.42\text{ mm}$) for camera tilt angles up to $60^\circ$.
    \item Multi-threaded pipeline execution achieved a frame rate of $34.4$~FPS ($29.09$~ms latency) with low resource usage ($142.5$~MB RAM, $24.8\%$ CPU).
    \item User typing tests showed an average typing speed of $24.6$~WPM with a Character Error Rate of $5.2\%$.
\end{itemize}

These evaluation results confirm that the virtual keyboard system provides reliable, low-latency performance on standard consumer hardware.
