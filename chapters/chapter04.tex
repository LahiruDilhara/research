\section{Chapter Overview}
\label{sec:req_chapter_overview}
The engineering of a reliable, high-performance, and customizable monocular paper virtual keyboard system requires a formal, comprehensive System Requirement Specification (SRS). Building markerless vision-based human-computer interaction (HCI) software demands rigorous systems analysis to ensure that real-time computer vision algorithms, kinematic scale normalization models, planar homography tracking engines, and deep neural classifiers satisfy operational requirements across diverse user groups \cite{ReviewVirtualKeyboard2020, Maman2023TypeNet}.

This chapter details the formal requirement specifications and unified modeling architecture governing the two-application suite: Application 1 (Layout Designer Suite \texttt{designer/designer\_app.py}) and Application 2 (Runtime Virtual Keyboard Engine \& Command Mapper). Section~\ref{sec:req_stakeholder} presents a structured stakeholder analysis, defining primary, secondary, and system stakeholders alongside an Interest-Power matrix and requirement trade-off resolution protocols. Section~\ref{sec:req_operationalization} details the operationalization process, mapping research objectives and empirical data gathering to system requirements. Section~\ref{sec:req_uml_analysis} provides an exhaustive Unified Modeling Language (UML) analysis containing Use Case diagrams with formal specifications for all core use cases, Class diagrams with Class Responsibility Collaboration (CRC) breakdowns, Activity diagrams, Sequence diagrams, Statechart diagrams, and Deployment diagrams. Section~\ref{sec:req_architecture} presents the proposed end-to-end system architecture framework and architectural design patterns. Section~\ref{sec:req_fn_nfn} defines the complete set of Functional and Non-Functional requirements with detailed subsection breakdowns. Finally, Section~\ref{sec:req_summary} summarizes the chapter.

\section{Stakeholder Analysis}
\label{sec:req_stakeholder}
Stakeholder analysis identifies the individuals, groups, and system entities affected by or interacting with the virtual keyboard system. Establishing clear stakeholder profiles ensures that software capabilities address real-world operational needs \cite{ReviewVirtualKeyboard2020}.

\subsection{Stakeholder Identification and Classification}
\label{subsec:req_stakeholder_classification}
Stakeholders associated with the customizable paper virtual keyboard system are categorized into four primary groups:
\begin{enumerate}
    \item \textbf{Primary End-Users:} Operators who directly interact with the physical paper keyboard layouts to perform text entry, navigation, or computer control. This includes general desktop users, touch typists, and motor-impaired individuals requiring custom accessibility keypads \cite{Chen2024Gaze}.
    \item \textbf{Domain-Specific Specialists:} Professional users in specialized fields—such as digital audio workstation (DAW) sound engineers, industrial automation operators, CAD designers, and video editors—who require customizable macro trigger pads tailored to complex software workflows \cite{ReviewVirtualKeyboard2020}.
    \item \textbf{Clinical \& Healthcare Personnel:} Surgeons, ICU nurses, and cleanroom laboratory technicians operating in sterile medical environments where physical mechanical keyboards present severe bacterial pathogen transmission vectors \cite{ReviewVirtualKeyboard2020}.
    \item \textbf{System Engineers \& Researchers:} Computer vision researchers, software developers, and system administrators responsible for designing layouts, configuring XML schemas, training deep learning touch models (\texttt{run\_all.py}), and deploying the runtime engine across host environments.
\end{enumerate}

\subsection{Stakeholder Conflict Resolution and Requirement Trade-offs}
\label{subsec:req_conflict_resolution}
Conflicting priorities among stakeholder groups were systematically resolved through empirical trade-off analysis:
\begin{enumerate}
    \item \textbf{Real-Time FPS vs Compute Load (Typists vs Administrators):} Primary typists demand high sampling rates ($> 30\text{ FPS}$), while system administrators require low CPU utilization. This was resolved by sub-sampling video capture to 12 FPS (\texttt{resample\_12fps.py}) and selecting a lightweight uni-directional PyTorch LSTM ($< 1\text{ MB}$ parameter size), achieving $34.4\text{ FPS}$ throughput on standard quad-core CPUs.
    \item \textbf{Layout Flexibility vs Tracking Stability (Domain Specialists vs Vision Researchers):} Custom macro pads require arbitrary key geometries, which can obscure corner tracking markers. This was resolved by enforcing border AprilTag placement along layout margins, requiring only four unoccluded tag corner points to solve SVD homography $H$.
    \item \textbf{Sanitary Sheet Disposable Disposal vs Layout Persistence (Clinical Personnel vs System Admins):} Resolved by storing layout configurations in XML files, allowing physical paper sheets to be disposed of and reprinted instantly without altering system software configuration.
\end{enumerate}

\subsection{Qualitative Data Gathering from User Interactivity Studies}
Operationalizing user requirements involved structured interviews with 15 test participants representing diverse typing skills. Key findings indicated that fixed keyboard layouts restrict efficiency for specialized software applications. Users expressed a strong preference for custom macro arrangements, validating the functional requirement for Application 1 Layout Designer (\texttt{designer/designer\_app.py}).

\subsection{Empirical Kinematic Data Translation to Landmark Requirements}
Kinematic video analysis revealed that fingertip pixel displacement varies non-linearly with camera distance $Z$ and hand size. Normalizing keypoint distances relative to middle MCP hand length $L_{\text{hand}} = \|\mathbf{P}_9 - \mathbf{P}_0\|_2$ produced unitless position ratios $\mathbf{P}_i^{\text{norm}}$, translating empirical kinematic observations into a strict functional requirement for unitless scale normalization without low-pass filtering.

\subsection{Architectural Design Patterns Applied}
\label{subsec:req_design_patterns}
The software architecture incorporates recognized software design patterns to ensure maintainability:
\begin{enumerate}
    \item \textbf{Model-View-Controller (MVC):} Applied in Application 1 Layout Designer (\texttt{designer\_app.py}) to decouple the graphical rendering canvas (View) from underlying XML coordinate schemas (Model) and user drag actions (Controller).
    \item \textbf{Producer-Consumer Thread Queue:} Applied in Application 2 to buffer raw OpenCV video frames captured by \texttt{camera\_thread.py} into a thread-safe Queue consumed by the PyTorch model manager (\texttt{model\_manager.py}), preventing frame drop.
    \item \textbf{Strategy Pattern for Action Dispatching:} Encapsulates keystroke injection vs system shell command execution into interchangeable strategy objects.
    \item \textbf{Singleton Model Manager:} Ensures that heavy PyTorch neural model binaries (\texttt{best\_finger\_touch\_lstm.pth}) are loaded into RAM once upon application launch.
\end{enumerate}

\subsection{Detailed Functional Requirements Subsection Breakdown}
\label{subsec:req_fr_details}
The 18 functional requirements are operationalized across four key subsystem domains:
\begin{enumerate}
    \item \textbf{Layout Designer Domain (FR-01 to FR-04):} Implemented in Application 1 (\texttt{designer/designer\_app.py}). Guarantees that layout creation, button bounding box calculations, AprilTag anchor placement, PDF vector rendering, and XML schema generation execute seamlessly.

\end{enumerate}

\subsection{Detailed Non-Functional Quality Constraints}
\label{subsec:req_nfr_details}
The 10 non-functional requirements enforce critical operational performance boundaries:
\begin{itemize}
    \item \textbf{Performance and Real-Time Execution (NFR-01, NFR-06):} The system guarantees an end-to-end frame processing latency of $29.09\text{ ms}$ ($\approx 34.4\text{ FPS}$) on standard desktop CPUs without requiring high-cost discrete GPUs.
    \item \textbf{Machine Learning Classification Accuracy (NFR-02):} The optimal PyTorch LSTM model trained on 5-frame scale-normalized feature windows achieves a touch classification F1-score of $0.963$ across all five digits.
    \item \textbf{Tracking Precision and Planar Tilt Robustness (NFR-03, NFR-04):} AprilTag corner localization achieves sub-pixel accuracy ($0.038\text{ px}$), enabling stable SVD homography calculation under planar inclination angles up to $75^\circ$.
    \item \textbf{GDPR Biometric Data Privacy Compliance (NFR-08):} The system processes video frames locally in temporary RAM buffers and permanently discards raw camera images afterMediaPipe landmark extraction, storing only anonymized scale-normalized coordinate arrays ($(x_i^{\text{norm}}, y_i^{\text{norm}})$).
\end{itemize}
